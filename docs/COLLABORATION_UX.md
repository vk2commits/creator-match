# 7차 UX 검토 · 고객 적합 분석과 한 명씩 이어지는 문의

2026-09-21. 지원자가 6차를 가장 나은 버전으로 평가한 뒤 지적한 문제를 수정했다. **구현·로컬 검증 후 사용자 재검토 단계**다. 사람 대상 사용성 테스트나 과제 제출 완료를 뜻하지 않는다. 모바일 추가 작업은 하지 않았다.

## 이번에 해결할 과업

브랜드 실무 마케터가 ‘조건을 충족한 후보’를 발견하는 데서 끝나지 않고, **우리 제품의 고객에게 어떻게 소개할지 설명하고, 선택한 한 명에게 연락한 뒤 결과까지 기록**할 수 있어야 한다.

| 사용자의 관찰 | 원인 | 적용한 변경 |
|---|---|---|
| ‘담았어요’, ‘비교 선택됨’이 모호함 | 상태 설명이 버튼의 다음 행동을 대신함 | 담기 취소 / 비교표에 추가·비교표에서 빼기 |
| 모든 지표에 ‘중요’가 붙음 | 균등 비중에서 강조의 의미가 사라짐 | 태그·중복 강조 제거, 결과 상단과 추천 문장으로 기준 전달 |
| ‘모르면 비워두세요’만 반복 | 어떤 값을 넣을지 알려주지 않음 | 실제 비용 1,000,000 / 조회수 25,000 등 단위에 맞는 예시 |
| 채널과 우리 고객이 왜 맞는지 모르겠음 | 지표 기반 검토와 콘텐츠 적합성 판단을 구분하지 않음 | 실제 추천 근거 뒤에 고객·예시 콘텐츠의 AI 분석 시연 |
| 한 사람에게 문의했는데 세 명이 나옴 | 문의 대상과 전체 팀 검토안의 범위를 혼동 | 누른 creator_id 한 명을 편집기로 전달; 팀 검토안 별도 경로 |
| 보낸 뒤 무엇을 하는지 모름 | 보내기 경험 없음, 상태 선택이 펼침 안에 숨음 | 명시한 발송 시연과 다음 단계 버튼, 목록·상세에서 상태 변경 |
| 단계마다 무엇을 기록할지 불명확함 | 모든 필드를 같은 긴 양식으로 취급 | 현재 단계에 필요한 문안/견적/제작/성과/미진행 사유 배치 |

## 두 가지 페르소나를 구분

- **서비스 사용자:** 브랜드 실무 마케터. 후보를 검토하고 팀에 설명하며 협업을 운영한다. 사용자가 직접 선택한 제품 대상이다.
- **캠페인의 타깃 고객:** 이번 제품을 소개할 사람. 마케터가 설명과 구매 판단 기준을 직접 정한다. 관측한 오디언스 분포가 아니다.

타깃 고객은 선택 입력이다. 이미 정한 사람만 입력하고, 아직 모르면 탐색을 먼저 진행한다. 상세에서 분석을 체험하려면 구매 판단 기준을 선택한다. 질문은 ‘사용 과정과 장단점을 비교하는가’, ‘일상에서의 쓰임을 보는가’, ‘새로운 취향을 찾는가’다. 나이·성별만으로 채널과 잘 맞는다고 단정하지 않는다.

## 분석의 근거와 시연 범위

| 층 | 사용하는 자료 | 보여주는 판단 | 순위 영향 |
|---|---|---|---|
| 실제 추천 이유 | 원본 CSV·적격 조건·사용자 비중 | 현재 기준에서 어떤 지표 때문에 검토하는가 | 기존 추천 함수가 결정 |
| 고객·콘텐츠 AI 시연 | 사용자가 고른 구매 판단 유형·별도 합성 콘텐츠 | 고객의 관심을 끌 방식, 조율할 점, 제작 요청 | 없음 |
| 집행 후 회고 | 사용자가 입력한 성과·비용·날짜·출처 | 확인한 성과와 비용 효율 | 없음 |

시연의 문장 구조는 **고객의 필요 → 살펴본 예시 → 연결 이유 → 제작 요청 → 선정 전 확인**이다. 고객 유형과 채널 예시가 다르면 ‘잘 맞는다’를 강요하지 않고 조율할 내용을 제안한다.

실제 예: 정은매거진77은 원본에서 조회 실적·평점·참고 비용으로 검토한다. 시연용 콘텐츠는 신제품과 스타일 제안으로 설정했다. ‘새 취향 발견’ 고객에게는 처음 관심을 끄는 구성이 맞는다고 설명하고, ‘일상에 대입’ 고객에게는 제품이 쓰이는 생활 장면을 추가하도록 제안한다. 실제 시청자가 직장인이라는 주장이나 구매 확률은 만들지 않는다.

시연은 세 가지 유형을 조합한 규칙 기반이다. 자유 입력한 제품·고객 문장을 범용 모델이 의미 분석하는 기능은 아니다. 예시 콘텐츠는 실제 채널 수집값이 아니며 상세에 명시한다. 실제 서비스에서는 공개·허가된 콘텐츠, 오디언스 집계, 광고 여부, 분석 시점, 출처를 확보하고 사용자 검토를 거쳐야 한다.

## 한 명의 문의에서 성과까지

| 상태 | 먼저 보이는 것 | 입력·확인할 값 | 다음 행동 | 빠진 값 처리 |
|---|---|---|---|---|
| 문의 준비 | 수신 대상 한 명과 보낼 문안 | 선택 제작 범위·일정·사용권, 실제 연락처 | 문의 보내기 · 시연 / 외부에서 보낸 문의 기록 | 문안 작성 가능. 외부 문의 기록은 실제 날짜 입력 필요 |
| 답변 대기 | 보낸 문안·시연 안내·답변 기록 안내 | 문의 날짜, 진행 메모 | 답변 받았어요 | 날짜 미입력은 보완 안내 |
| 조건 협의 | 받은 견적과 최종 합의 비용 | 제작 범위·게시일·사용권·답변 | 협업 확정하기 | 미확정 필드는 나중에 채워도 상태 기록 가능 |
| 제작 진행 | 최종 조건과 일정 | 합의 비용·제작 범위·게시일·진행 메모 | 게시 완료로 변경 | 부족한 항목을 명시 |
| 집행 완료 | 콘텐츠와 조회수·비용 | 링크·확인일·출처, 추가 반응·클릭·구매 | 저장하고 성과 리포트 보기 | 수치 입력 시 출처·날짜 필요, 구매는 집계 기준 필요 |
| 진행 안 함 | 미진행 사유 | 일정 불일치 등 이유 | 조건 협의로 다시 검토 | 사유 미작성은 보완 안내, 기존 데이터 보존 |

목록의 상태 변경은 바로 저장한다. 상세의 선택은 해당 단계 필드로 이동하며 ‘저장하고 닫기’ 또는 다음 단계 버튼으로 저장한다. 닫을 때 미저장 값이 있으면 저장/폐기/계속 작성 중 선택한다. 상태를 자유롭게 바꾸는 것과 잘못된 값을 저장하는 것은 다르다. 음수·잘못된 날짜·허용되지 않은 URL·성과 출처 누락 검사는 유지한다.

받은 견적과 합의 비용은 분리한다. 받은 금액을 합의 비용으로 옮길 때는 버튼을 직접 누른다. 실제 집행비는 다시 확인해 입력한다. 같은 금액이라고 자동으로 가정하지 않는다.

발송 시연은 외부 전송 없이 로컬에 보낸 문안과 시연 시각을 보관한다. 실제 문의 날짜는 만들지 않는다. 복사·이메일 초안 열기도 발송 완료로 처리하지 않는다. 이후 문안을 수정해도 보낸 문안은 유지한다. 후보별 기록은 서로 독립적이다.

## 추가 점검에서 고친 것

AI가 직접 발견한 항목이며 지원자가 발견했다고 기록하지 않는다.

- 기존 협업 기록이 있는데도 ‘문의 준비’가 보이는 문제: 카드·상세·비교표에서 ‘협업 기록 이어보기’로 변경.
- 제품 메시지가 완성 문장일 때 ‘…를 소개할 때’로 붙여 어색해지는 문제: 입력한 메시지와 제작 요청을 나눠 표시.
- 시연 분석 중 고객 수정 시 이전 대기 결과가 나타날 가능성: 진행 중 타이머 취소.
- 브리프의 ‘한 명당’ 인식 정규식 오류: 교정하고 실제 조건 해석 테스트 추가.
- PRD에 예전 온보딩·저장 버전·원본 ID 노출 정책이 남은 문제: 실제 화면 기준으로 갱신.

## 검증과 다음 사용자 리뷰

자동 검증과 실제 데스크톱 과업 결과는 [QA](QA.md)에 기록한다. 목표는 다음 세 과업에서 설명 없이 진행할 수 있는지 사용자에게 확인하는 것이다.

1. **이유 설명:** 상세를 읽고 이 후보를 고를 이유 한 가지와 아직 확인할 사항 한 가지를 말한다.
2. **한 명에게 문의:** 세 명을 비교한 뒤 원하는 한 명의 문의를 보내는 시연을 완료한다.
3. **후속 기록:** 답변·견적을 기록하고 상태를 변경한 뒤 성과 리포트까지 이동한다.

판단 기준은 과업 성공 여부, 첫 번째 잘못 누른 버튼, 멈춘 위치, 이해하지 못한 문구, 실제/시연 데이터의 구분이다. 소요 시간·성공률은 아직 측정하지 않았다.

남은 개선 후보의 우선순위는 다음과 같다. 지금 구현 완료로 표시하지 않는다.

| 우선순위 | 남은 문제/가설 | 다음 결정 기준 |
|---|---|---|
| 제출 전 | 새 분석까지 본 사용자가 추천 근거를 납득하는지 | 위 세 과업 사용자 리뷰. 어려우면 정보를 더 추가하기보다 문장·순서 수정 |
| 제출 전 | 선택 기능이 핵심 추천 설계를 가리지 않는지 | 3분 데모는 필터·우선순위·이유·한 명 문의에 집중, 성과는 짧게 |
| 실제 서비스 전 | 실제 고객·콘텐츠 적합성 | 콘텐츠·오디언스 근거 수집, 모델 출력의 사실성과 근거 연결 평가 |
| 실제 서비스 전 | 문안 발송·중복 발송·수신 동의·배달 실패 | 실제 발송 기능을 연결할 때 수신자 확인·재전송 방지·실패 복구 설계 |
| 확장 시 | 복수 캠페인·여러 콘텐츠·관측 시점 | 단일 작업실 범위를 넘는 수요 검증 후 별도 데이터 모델 |
| 확장 시 | 팀 승인과 Pro 과금 | 반복 보고·팀 권한·자동 수집의 지불 의향 검증. 추천 이유 자체는 잠그지 않음 |

모비데이즈의 명시 평가와 연결되는 차별점은 기능 개수가 아니라 **실제 추천 근거, 시연 가설, 관측 성과를 구분하고 사용자 피드백으로 정책까지 바꾼 기록**이다. 다른 지원자의 결과물을 보지 않았으므로 독점적 차별성은 주장하지 않는다.
