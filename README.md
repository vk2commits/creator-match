# Creator Match

**브랜드 실무 마케터가 예산 안의 크리에이터를 추리고, 선택 이유를 설명한 뒤 협업을 준비하는 웹앱입니다.**

제공된 200명 CSV로 후보를 추천합니다. 핵심은 **조건 통과 여부와 추천 순위를 분리하고, 확인되지 않은 비용·평점·콘텐츠를 있는 것처럼 해석하지 않는 것**입니다. React·TypeScript·Vite로 구현했으며 기본 실행에는 로그인, API 키, 데이터베이스가 필요 없습니다.

## 실행

Node.js **22.12 이상**과 npm이 필요합니다. 검증 환경은 macOS / Node 25.5.0 / npm 11.8.0입니다.

```sh
npm ci
npm run dev
```

터미널에 표시되는 주소를 엽니다. 기본 주소는 `http://127.0.0.1:5173/`입니다. `index.html` 파일을 직접 열어 실행하는 방식은 지원하지 않습니다.

```sh
npm run check     # 자동 테스트 + 타입 검사 + 빌드
npm run preview   # 빌드 결과 확인
npm run analyze   # 데이터 감사·추천 대안·비중 비교 재생성
node --import tsx scripts/review-logic.ts  # 추천 민감도·반례 진단
```

## 3분 검토 경로

1. `http://127.0.0.1:5173/?demo`에서 **예시 문장 넣기 → 캠페인 초안 만들기**를 선택합니다. 일반 캠페인과 분리된 탭 저장 공간입니다.
2. **캠페인·고객 → 후보 조건 → 추천 기준**을 확인합니다. 모든 단계는 왼쪽 안내·오른쪽 입력 구조입니다. 예시는 뷰티·패션 / 1명당 200만 원 / 마이크로입니다.
3. 추천 **21명**, 비용 미확인 **3명**을 확인합니다. 조회수 우선의 첫 후보는 **정은매거진77**입니다. 상세의 설명과 **적용한 추천 기준 보기**에서 실제 비중·비교 집단을 확인합니다.
4. **기준·비중 변경 → 참여율 우선 → 적용**하면 첫 후보가 **서연리뷰66**으로 바뀝니다. 후보 자격은 그대로이고 순위만 바뀝니다. 직접 슬라이더 조절도 가능합니다.
5. 같은 조건에서 예산을 **1원**으로 바꾸면 적격 후보가 없어집니다. 제안된 **540,000원**을 직접 적용하면 **소라TV177 한 명**이 나옵니다. 비용 미확인 후보는 계속 별도로 확인할 수 있습니다.

선택 기능은 **민준브이로그180 → 적합 분석 → 근거 확인 → 제안 담아 문의하기**로 살펴볼 수 있습니다. 이 후보의 콘텐츠·댓글 자료는 별도 편집 예시입니다. 문의·협업 상태와 게시 후 성과를 기록할 수 있지만 실제 이메일·DM은 발송되지 않습니다.

## 추천 설계에서 내린 판단

| 결정 | 이유 | 감수한 한계 |
|---|---|---|
| 예산·분야·규모는 필터, 네 지표는 순위 | 조건 충족을 다시 점수로 더하지 않아 중복 가산을 피함 | 여러 명의 총예산 배분은 해결하지 않음 |
| 참여율·조회수는 플랫폼×규모 내 상대 위치 | 큰 채널과 플랫폼 차이가 순위를 지배하는 현상을 줄이기 위한 선택 | 기간·형식·카테고리 차이까지 보정하지 못함 |
| 평점은 1–5 척도, 경험은 로그 변환 | 평점 표본 수를 만들지 않고, 경험이 많을수록 가산 폭을 줄임 | 평점 신뢰도를 추정할 수 없고 신규 후보를 동일하게 평가하기 어려움 |
| 목표별 시작 비중 + 사용자 조절 | 하나의 고정 비중을 모든 광고주의 정답으로 가정하지 않음 | 비중은 학습한 최적값이 아닌 제품 가정 |
| 비용 미확인 27명을 별도 노출 | 0원을 무료, 공란 평점을 낮은 평가로 오해하지 않게 함 | 현재 견적을 받기 전에는 예산 적합 여부를 판단할 수 없음 |

수식·가중치·동점·결측 정책은 [PRD](PRD.md), 분기와 복구 경로는 [flowchart](flowchart.md)에 있습니다.

**대안 검증:** 같은 후보 자격에 A=팔로워순, B=전체 데이터 상대 점수, C=플랫폼×규모 상대 점수를 적용했습니다. 150개 조건 중 76개에 후보가 있었고, C의 조건 위반은 0건입니다. A–C의 1위는 45개, B–C는 14개 조건에서 달랐습니다. 균등 비중의 상대 ±20% 변경 608회에서 1위 변경은 35회였습니다. 이는 정책 준수와 민감도에 대한 증거이며 **C의 실제 광고 성과가 더 좋다는 증거는 아닙니다.** [실험 상세](docs/EVALUATION.md)

## 경쟁사 조사와 우리 설계의 구분

피처링·TAGby·REVU·Modash·HypeAuditor·CreatorIQ에서 탐색→검토→협업으로 이어지는 업무와 근거를 확인하는 방식을 참고했습니다. 경쟁사의 내부 추천 수식이나 유료 제품을 재현한 것은 아닙니다. [공식 자료 기반 비교](docs/COMPETITOR_DEEP_DIVE.md)

이번 결과물에서 강조하는 설계는 **미확인 후보의 별도 처리, 사용자가 바꿀 수 있는 비교 기준, 같은 데이터로 재현하는 대안 실험, 분석 근거를 문의 질문으로 연결하는 흐름**입니다. 경쟁사에 없는 독점 기능이라는 주장이 아니라, 제공 데이터와 과제 목적에 맞춰 선택한 설계입니다.

## 데이터와 구현의 경계

- CSV 200명과 11개 필드를 그대로 보존합니다. 집행 이력이 있는 173명은 평균 비용×건수와 누적액이 다릅니다. 원본을 수정하지 않고 예산 필터에는 제공된 평균 비용을 사용합니다. [감사·해시](docs/DATA_AUDIT.md)
- 원본에는 실제 SNS 주소, 광고별 성과, 타깃 오디언스가 없습니다. 별도 구성한 **5명 콘텐츠 예시와 AI 생성 이미지 2개**는 상세·리포트에서 출처를 구분하며 추천 점수에 가산하지 않습니다.
- 온보딩 문장 정리·문의 문안·성과 요약은 현재 로컬 규칙입니다. 검색·후보 분석은 키 없이도 동작하며, `.env.example`의 서버 환경변수로 선택적 모델 연결이 가능합니다. **실제 모델 연결 성공·품질·비용은 이번 환경에서 검증하지 않았습니다.** 키를 공개하거나 `VITE_` 변수에 넣지 않습니다. 정적 배포에는 로컬 서버 기능이 포함되지 않습니다.
- 일반 실행은 localStorage, `?demo`는 별도 sessionStorage에 저장합니다. 캠페인별 조건·후보·문의·성과는 분리하고, 직접 등록한 채널 자료는 공통으로 사용합니다. 온보딩 미확정 입력의 새로고침 복구는 지원하지 않습니다.
- 성과는 사용자가 입력한 최신 누적 기록입니다. 관측값과 예측값을 혼합하거나 추천 모델의 학습 결과로 사용하지 않습니다. 자동 수집·실제 발송·결제·공동 편집·모바일 최적화는 범위 밖입니다.
- 분석 리포트의 **내용 복사**는 확인했습니다. 앱 안 브라우저의 파일 다운로드 완료, 공개 GitHub 화면의 Mermaid 렌더링, 실제 사용자 사용성 평가는 최종 검토 대상으로 남깁니다.
